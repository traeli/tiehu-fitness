# 1.0.3 内容需求

版本：V1.0.3  
状态：需求草案；六类内容场景已确认，场景选择方式与 API 兼容细节待确认  
适用范围：`core-service`、`vision-service` 与 `utools-ai-meeting-assistant`

## 1. 版本目标

V1.0.3 解决历史录音与总结不联动、实时转写区域利用不足、总结结构只适合会议，以及用户额度和平台 ASR 能力错误混淆的问题。

本版本不新增第三个服务，不为不同内容场景新增独立数据表。API 变更必须先修改 Proto 并重新生成代码；已经发布的字段编号和含义必须保持兼容。

## 2. 历史录音与 AI 总结联动

### 2.1 当前问题

- 历史录音详情使用 `recordingSummary`，页面底部独立的 `AI SUMMARY` 使用全局 `summary`。
- 点击不同录音时只会更新历史详情，页面底部仍可能展示上一场刚结束会议的总结。
- 底部导出操作同样读取全局 `summary`，不能保证导出的是当前选中录音。

### 2.2 需求

1. AI 总结必须与当前选中的本地录音及其 `meeting_id` 严格绑定。
2. 删除页面底部独立的 `AI SUMMARY` 区域，将总结统一放入当前选中录音的详情区域。
3. 点击另一条录音后，立即清空上一条录音的播放地址、转写内容、总结内容和失败信息，并显示加载状态。
4. 录音、会议状态、最终转写和总结均按当前录音关联的 `meeting_id` 加载。
5. 异步请求必须携带前端选择版本。旧选择的请求晚于新选择返回时，结果必须被忽略，不能覆盖当前页面。
6. 导出 Markdown 必须导出当前选中录音的总结；总结未加载成功时不允许导出。
7. 一场新录音保存完成后，刷新历史列表。是否自动选中新录音由实现阶段根据交互连贯性决定，但不得继续展示上一场总结冒充新录音结果。

### 2.3 页面文案

- 未选择录音：`点击左侧录音，可回放音频并查看完整转写与 AI 总结。`
- 正在加载：`正在加载录音和内容…`
- 尚未生成：`该内容尚未生成 AI 总结。`
- 生成中：`正在生成 AI 总结…`
- 生成失败：`AI 总结生成失败，可稍后重新生成。`

### 2.4 验收标准

- 连续点击两条具有不同总结的录音，标题、概述、详情和导出内容均随当前录音变化。
- 快速来回切换录音时，不出现旧请求覆盖新选择。
- 页面不存在第二个脱离当前选择状态的总结区域。

## 3. 实时转写区域优化

### 3.1 当前问题

- 实时转写列表固定使用 `max-height: 290px`，没有利用卡片下方剩余空间。
- 新片段到达后没有自动跟随最新内容。
- 临时结果、最终结果和“已收到音频但尚未出字”的状态缺少清晰反馈。

### 3.2 需求

1. 实时转写区域使用卡片全部可用高度，内容超出后仅在列表内部滚动。
2. 用户位于列表底部时，新片段到达后自动滚动到最新内容。
3. 用户主动向上查看历史内容时，不得强制拉回底部；此时显示 `有新内容` 按钮，点击后回到最新片段。
4. 临时识别片段可以实时展示，最终片段到达后按稳定片段 ID 或序号替换临时内容，不得产生重复文本。
5. 停止会议后保留当前实时文字，直到用户开始下一场会议或选中历史录音。
6. 长时间转写需要保持渲染有界；首版可以限制 DOM 中的实时片段数量，服务端最终转写仍须完整保存。

### 3.3 状态文案

- 尚未开始：`开始录制后，转写内容会显示在这里。`
- 等待音频：`正在等待语音…`
- 已有音频、暂无文字：`已收到音频，正在识别…`
- 实时连接中断：`实时转写已中断，本地录音仍会保留。`
- 有未读片段：`有新内容`

### 3.4 验收标准

- 转写列表能使用实时内容卡片的剩余高度，不再固定只显示约 290px。
- 连续产生片段时默认可看到最新文字。
- 用户向上滚动后，新片段不会打断阅读。
- 临时片段转为最终片段时不重复。

## 4. 内容自适应 AI 总结（待确认设计）

### 4.1 当前实现核对

当前整条链路都以固定会议纪要为模型：

- 公共 Proto `MeetingSummary` 固定包含 `topic`、`abstract`、`key_discussions`、`decisions`、`action_items` 和 `risks`。
- vision 领域对象和 DeepSeek 响应校验使用同一组固定字段。
- DeepSeek `meeting-summary-v2` 虽然说明输入可能是会议、课程、访谈、播客或媒体，但仍强制模型输出会议字段。
- core 将经过校验的固定结构存入 `meetings.summary_content`。
- uTools 使用固定会议总结组件和固定 Markdown 章节。

因此，当前问题不仅是页面标题写死，而是 Proto、领域对象、Provider 输出、持久化映射和客户端模型全部被“会议字段”约束。

### 4.2 不采用的方案

不为会议、学习视频、电影、歌曲、播客或相声分别增加数据库表，也不在 `meetings` 表增加大量仅对某一种场景有效的可空列。

原因：

- 场景增加时需要持续修改表结构。
- 大量字段在多数记录中为空。
- 查询、兼容和排错复杂度上升。
- 与当前收紧会议相关表结构的方向冲突。

也不直接采用完全自由的 `sections: [{title, content}]` 作为唯一公共契约。它虽然灵活，但会失去类型校验、字段语义和前端稳定渲染能力，并可能形成不受限制的 JSON 输出。

### 4.3 推荐方案：统一外壳 + 场景类型 + 场景专属详情

所有总结共享少量通用字段，具体内容通过受约束的场景专属结构表达：

```text
schema_version
content_type
topic
abstract
details（按 content_type 只能出现一种）
```

字段含义：

- `schema_version`：总结内容结构版本，用于兼容历史数据。
- `content_type`：经过校验的内容类型枚举。
- `topic`：通用标题。API 为兼容现有字段继续使用 `topic`，UI 可显示为“标题”。
- `abstract`：通用概述。API 为兼容现有字段继续使用 `abstract`，UI 可显示为“内容概述”。
- `details`：与 `content_type` 匹配的场景专属结构；Proto 使用 `oneof` 表达，Go 领域层使用明确类型，不使用 `map[string]any`。

V1.0.3 确认支持以下六类内容及对应字段：

#### 4.3.1 会议 `MEETING`

```text
key_discussions
decisions
action_items { assignee, task, due_text, status }
risks_and_open_questions
```

UI 使用会议总结组件，展示“讨论重点、形成结论、行动事项、风险与待确认”。空模块不显示。

#### 4.3.2 学习内容 `LEARNING`

```text
key_concepts
knowledge_points
methods_or_steps
examples
review_points
```

UI 使用学习笔记组件，展示“核心概念、知识要点、方法步骤、示例、复习清单”。

#### 4.3.3 影视或叙事内容 `NARRATIVE`

```text
characters
key_events
themes
notable_details
```

UI 使用影视内容组件，展示“内容梗概、人物与关系、关键情节、主题表达、值得注意的细节”。`abstract` 承担内容梗概，避免重复存储 `synopsis`。

#### 4.3.4 访谈、播客或谈话节目 `SPOKEN_PROGRAM`

```text
topics
viewpoints
highlights
takeaways
```

UI 使用谈话内容组件，展示“主要话题、重要观点、精彩内容、值得带走的内容”。相声归入这一类，V1.0.3 不增加独立 `COMEDY` 类型。

#### 4.3.5 歌曲或音乐内容 `MUSIC`

```text
themes
mood
imagery
interpretation
```

UI 使用音乐内容组件，展示“主题、情绪氛围、意象、内容解读”。不保存或输出大段歌词原文。

#### 4.3.6 无法可靠分类 `GENERAL`

```text
main_points
highlights
structure
takeaways
```

UI 使用通用内容组件，展示“主要内容、重点、内容结构、值得回顾”。

### 4.4 UI 不是统一章节列表

前端只共享总结卡片外壳、标题、概述、状态和导出按钮。详情区域根据 `content_type` 选择不同组件：

```text
SummaryContainer
├── MeetingSummaryView
├── LearningSummaryView
├── NarrativeSummaryView
├── SpokenProgramSummaryView
├── MusicSummaryView
└── GeneralSummaryView
```

每个组件拥有自己的字段标题、展示顺序和版式。不能把所有类型都渲染成“关键讨论、核心决定、待办事项、风险”，也不能显示当前场景不存在的空模块。

### 4.5 后端存储建议

继续使用现有 `meetings.summary_content JSONB` 保存最终可展示总结，不新增场景总结表：

```json
{
  "schema_version": 2,
  "content_type": "learning",
  "topic": "力量训练中的渐进超负荷",
  "abstract": "内容介绍了渐进增加训练刺激的基本原则。",
  "details": {
    "key_concepts": [],
    "knowledge_points": [],
    "methods_or_steps": [],
    "examples": [],
    "review_points": []
  }
}
```

约束：

1. JSONB 只是持久化形式，不能在 biz 中作为任意 JSON 透传。
2. core 和 vision 都必须按 `content_type` 解析成明确的领域类型并执行长度、数量和类型校验。
3. `details` 必须与 `content_type` 匹配；未知类型、字段错配或超限结果按 `SUMMARY_OUTPUT_INVALID` 处理。
4. `meeting_summary_jobs.result_json` 保存 vision 已校验的同一版本结构；`llm_response` 继续仅用于服务端排错。
5. 暂不增加 `summary_content_type` 独立数据库列。只有后续出现按内容类型筛选、统计或建立索引的真实需求时再通过迁移增加。
6. 每种列表和文本都必须设置上限，不能允许模型产生无界数据。

### 4.6 API 兼容建议

1. 保留已经发布的 `MeetingSummary` 字段编号 1 至 15，不删除、不重命名、不复用。
2. 新增 `ContentType` Proto 枚举，包含 `UNSPECIFIED = 0`。
3. 在现有消息末尾增加 `content_type` 和场景 `oneof details`，或新增被现有响应引用的版本化内容消息；具体 Proto 形式在实现前确定。
4. 旧的 `key_discussions`、`decisions`、`action_items` 和 `risks` 仅在会议类型中继续填充，供旧客户端兼容。
5. 历史 `summary_content` 未包含 `schema_version` 时按版本 1 的会议总结读取，无需一次性重写线上历史数据。
6. V1.0.3 客户端优先读取新结构；新结构不存在时把旧字段适配为会议总结。

### 4.7 场景选择与识别（待讨论）

仅依赖 LLM 自动分类可能把电影对白识别成会议，也可能把课程讨论识别成普通谈话。推荐提供：

- 默认选项：`智能识别`
- 可选指定：`会议`、`学习`、`影视`、`访谈/播客`、`音乐`、`通用`

需要区分两个概念：

- `requested_content_type`：用户开始录制时选择的偏好；`AUTO` 表示由模型判断。
- `content_type`：最终总结实际采用的类型。

用户选定明确类型时，LLM 不再自行切换类型；选择智能识别时，由同一次总结调用完成分类和总结，避免额外增加一次 LLM 调用。后续可支持用户在历史详情中修改类型并重新生成。

### 4.8 本节待确认事项

在编码前需要确认：

1. 是否接受“统一 JSONB 外壳 + Proto `oneof` 场景详情 + 场景化 UI 组件”的总体方案。
2. 开始录制前是否展示内容类型选择器；推荐默认智能识别并允许用户手动指定。
3. 是否在历史详情中支持“更改内容类型并重新生成”；建议本版本至少预留 API 语义，UI 可以后续上线。

## 5. 用户额度与平台 ASR 能力错误处理

### 5.1 两类额度必须分开

- 用户额度：会议助手分配给当前用户的月度转写时长。
- 平台能力：服务端百炼账号的免费额度、账户余额、模型权限、并发和限流状态。

平台额度耗尽不能向用户显示“你的额度已用完”，也不能统一映射为 `UNKNOWN_ERROR`。

### 5.2 用户月度额度用完

创建会议前返回稳定错误：

```text
HTTP 429
reason: MEETING_QUOTA_EXCEEDED
retryable: false
```

用户端文案：

```text
本月转写额度已用完
本月可用转写时长已全部使用，额度将在 {重置日期} 恢复。购买额外额度后也可以继续使用。
```

会议过程中用完额度时：

1. vision 发送 WebSocket 错误 `MEETING_QUOTA_EXCEEDED`。
2. vision 随后发送 `session_finished`，`finish_reason = quota_exhausted`，并正常关闭 WSS。
3. 客户端停止采集并保存本地录音。
4. 服务端按实际规则完成结算并释放活动会议占用。
5. 已产生的最终转写仍可生成总结。

用户端文案：

```text
转写额度已用完
会议已停止，录音已保存在本地。已完成的转写和 AI 总结仍可查看。
```

### 5.3 百炼额度、余额或权限不可用

面向客户端统一返回脱敏错误：

```text
HTTP 503
reason: ASR_PROVIDER_UNAVAILABLE
retryable: true
```

用户端文案：

```text
云端转写服务暂时不可用
本次会议未扣除转写额度，请稍后重试。
```

要求：

1. 服务端日志记录安全的 Provider HTTP 状态码、Provider 错误码、模型和请求 ID，但不记录 API Key。
2. 平台能力失败时释放用户额度预占和活动会议占用，本次失败不扣用户额度。
3. Provider 403 配额耗尽和 429 短期限流必须在服务端区分；客户端可以分别显示“服务暂不可用”和“服务繁忙”。
4. 对 Provider 配额耗尽、余额不足、持续限流设置运维告警。

### 5.4 百炼额度查询结论

百炼提供 `GET /api/v1/models/limits`，用于查询模型的 RPM、QPS、TPM 等请求频率和窗口用量限制，但它不是免费额度或账户余额的实时剩余接口：

- [百炼查询模型限额](https://help.aliyun.com/zh/model-studio/list-quotas)

免费额度剩余量主要在百炼控制台查看，控制台数据为分钟级更新；模型用量统计还可能有约一小时延迟：

- [百炼模型用量](https://help.aliyun.com/zh/model-studio/model-usage-statistics)

因此 V1.0.3 不依赖启动前查询“百炼实时剩余额度”。运行时按 Provider 的明确错误码判断并熔断、告警：

- `403 AllocationQuota.FreeTierOnly`：平台免费额度耗尽或“用完即停”生效。
- `429`：Provider RPM、QPS 或 TPM 限流，按退避策略短暂重试。
- 其他鉴权、模型权限和服务故障：映射为 Provider 不可用，保留脱敏内部原因。

若产品需要持续对外提供服务，应开通按量付费并设置费用告警，同时准备可在数据库实时切换的备用 ASR 模型或 Provider，不能把免费额度作为长期可用性保障。

## 6. 推荐实施顺序

1. 修复历史录音、总结和 Markdown 导出的选择状态绑定。
2. 调整实时转写布局、自动滚动和临时/最终片段更新。
3. 确认第 4 节的内容类型集合、用户选择方式和 Proto 兼容方案。
4. Proto 优先增加内容类型与场景详情，重新生成代码并检查 OpenAPI。
5. 修改 vision 领域模型、DeepSeek Prompt V3、响应解析和有界校验。
6. 修改 core 领域模型及 `summary_content` 版本化持久化映射。
7. 增加不同内容类型的前端组件和 Markdown 导出模板。
8. 完善用户额度与 Provider 能力错误映射、结算和告警。
9. 为历史兼容、快速切换、错误映射和各场景总结增加回归测试。

## 7. V1.0.3 完成标准

- 历史录音、播放、完整转写、AI 总结和 Markdown 导出始终属于同一个 `meeting_id`。
- 实时转写充分使用页面空间，自动跟随最新内容且不打断用户阅读历史文字。
- 会议、学习、影视、谈话、音乐等内容不再共用固定会议字段和固定会议 UI。
- 总结内容通过明确领域类型和 Proto 枚举校验，数据库不新增按场景拆分的表。
- 历史版本 1 总结仍然可以读取和展示。
- 用户额度耗尽与百炼平台不可用具有不同的稳定错误、文案和结算行为。
- Provider 原始错误不泄露给客户端，API Key 不进入日志或响应。
