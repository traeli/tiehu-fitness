## 2. 本轮交付目标

本轮交付“实时语音转写后端闭环”：

```text
uTools 登录
  -> core-service 创建会议
  -> core 调用 vision 准备 ASR session
  -> vision 返回一次性 WSS ticket
  -> uTools 直连 vision-service
  -> vision 连接 paraformer-realtime-v2
  -> 实时临时/最终文本返回 uTools
  -> 最终片段可靠同步并持久化到 core
  -> 停止会议时刷新最后一句并结束 ASR session
```

达到本轮完成标准后，应能使用真实百炼 Key 完成一次端到端会议转写，但自动化测试不能消耗真实百炼额度。

### 2.1 本轮包含

- uTools 临时令牌登录 core-service。
- core access token 鉴权中间件和当前用户上下文。
- 单用户月度分钟数、单场时长、并发会议和创建频率限制。
- 配额预占、实时用量上报、停止结算和异常释放。
- core 会议创建、停止、查询和最终转写分页查询。
- core 与 vision 的内部 gRPC 合同。
- core、vision 共享 Redis 基础设施，但使用独立 ACL 和 key 前缀。
- vision 一次性 WebSocket ticket。
- vision 实时转写领域、状态机和 Provider 接口。
- 阿里百炼 `paraformer-realtime-v2` WebSocket adapter。
- vision 对外业务 WebSocket、ACK、心跳、revision、finish 和稳定错误。
- 最终转写片段从 vision 幂等同步到 core。
- PostgreSQL migration、GORM repository、测试和可观测性。
- Fake Provider、Fake Redis 或 Redis 集成测试以及真实环境冒烟说明。

### 2.2 本轮不包含

- LLM 会议纪要生成。
- Markdown/PDF/TXT 服务端导出。
- 屏幕录制、OCR、VLM 和 PPT 理解。
- 实时说话人身份识别。
- 订阅支付和正式商业计费。
- `paraformer-v2` 全量会后文件识别。
- 第二家 ASR Provider。
- 新建第三个 deployable service。

会后 `paraformer-v2` 校正作为本计划末尾的后续工作包，不计入本轮实时 ASR 完成率。

## 3. 固定架构决策

后续 Agent 不应在实施中重新选择以下架构：

| 决策项 | 固定结论 |
|---|---|
| Go 工程 | 保持根目录单一 `go.mod` |
| 服务数量 | 只使用 core-service 和 vision-service |
| 框架 | Kratos v3 + Protobuf + gRPC/HTTP |
| core 职责 | 用户、鉴权、会议、额度、最终转写所有权 |
| 配额事实来源 | core PostgreSQL 用量账本；Redis 只做短期限流/并发辅助 |
| 默认并发 | 每个用户最多 1 场活跃会议，可由服务端策略调整 |
| 实时执行 | core 授予本次最大音频秒数，vision 到达上限立即停止接收 |
| vision 职责 | ticket、媒体、实时 ASR、Provider、AI attempt |
| 实时公网通道 | uTools 使用一次性 ticket 直连 vision WebSocket |
| 服务间通道 | core 与 vision 使用内部 gRPC；可靠异步场景使用 outbox |
| ASR Provider | 阿里云百炼 |
| 实时模型 | `paraformer-realtime-v2` |
| 实时音频 | PCM16LE、16kHz、mono、100～200ms 分片 |
| 实时输出 | WebSocket，不使用 SSE |
| 密钥 | 只存在 vision 部署环境 |
| Redis | 同一实例可复用，core/vision 使用独立 ACL 和前缀 |
| 数据库 | core 与 vision 独立数据库，禁止跨库查询和外键 |

实时音频不经过 core-service 转发。core 是控制面，vision 是实时音频数据面。

## 5. Agent 执行约束

### 5.1 每个工作包开始前

Agent 必须：

1. 完整读取根目录 `AGENTS.md`。
2. 读取本计划和 Paraformer 接入方案中的相关章节。
3. 执行 `git status --short`，确认工作区已有改动。
4. 检查目标文件当前内容，不能依据旧上下文直接覆盖。
5. 判断本工作包是否改变 Proto、数据库、配置或公开协议。
6. 在本文件的进度表中把当前工作包更新为“进行中”。

如果 CodeGraph 已初始化，结构查询优先使用 CodeGraph；如果没有 `.codegraph/`，不得擅自初始化，先向用户确认。

### 5.2 实施规则

- 严格遵循 `server -> service -> biz <- data`。
- API 先改 Proto，再生成代码，再实现 biz、data、service 和 server。
- 不手工修改 `*.pb.go`、`*_grpc.pb.go`、`*_http.pb.go`、`internal/conf/conf.pb.go` 或 `openapi.yaml`。
- migration 使用下一个未占用序号，同时提供 `.up.sql` 和 `.down.sql`。
- 不修改已经存在的 migration 来加入会议表。
- 所有闭集在 biz 使用领域类型，在 Proto 使用含 `UNSPECIFIED = 0` 的 enum。
- 所有外部字符串、枚举、UUID、数值、指针和集合访问显式校验。
- 预期失败返回错误，不 panic。
- 每个 goroutine 有 owner、context、截止时间、有界队列和 panic recovery。
- 不将 Provider 原始错误、SQL、Key、token、音频或转写正文返回客户端或写日志。
- 自动化测试使用 fake，不调用真实 uTools 或百炼。
- 不为通过测试而返回空成功对象、忽略错误或降低校验。

### 5.3 每个工作包结束后

Agent 必须：

1. 运行该工作包要求的最小验证。
2. 运行 `git diff --check`。
3. 更新本计划的进度、完成日期、验证结果和剩余限制。
4. 列出实际修改文件，不声称未运行的测试通过。
5. 发现跨工作包问题时记录在“风险与决策日志”，不要无边界扩展当前任务。

## 11. B-350：单用户配额与用量账本

目标：在创建会议前原子检查并预占用户额度，在实时转写过程中执行硬上限，在停止、失败和过期时准确结算或释放，防止单个用户产生无上限的 ASR 成本。

### 11.1 限额维度

V1 必须同时支持：

- 月度音频秒数上限。
- 单场会议最大音频秒数。
- 单用户同时活跃会议数。
- 单用户创建会议请求频率。
- 单个 session 最大实时连接数，只允许一个活跃数据连接。

建议初始默认策略：

| 限制 | 建议默认值 | 说明 |
|---|---:|---|
| 免费用户月度额度 | 7,200 秒（120 分钟） | 配置项，不硬编码到 biz |
| 单场会议上限 | 14,400 秒（4 小时） | 实际 grant 取单场上限与剩余额度的较小值 |
| 同时活跃会议 | 1 | 防止同一额度被并发透支 |
| 创建会议频率 | 10 分钟最多 5 次 | Redis 限流，防止 ticket/Provider 资源滥用 |
| 用量上报间隔 | 30 秒 | vision 使用累计值上报，停止时强制上报 |

产品值全部来自经过校验的 core quota 配置或用户 override。后续会员/企业套餐只替换策略来源，不改变 reservation 和 ledger 算法。

### 11.2 计费周期和计量口径

- V1 月度周期按 `Asia/Shanghai` 自然月计算，周期边界以 UTC `TIMESTAMPTZ` 保存。
- 用户额度按 vision 实际接受并发送到 ASR 队列的 PCM 音频秒数计算。
- PCM16LE/16kHz/mono 每秒为 32,000 字节；服务端按累计有效字节计算，不信任客户端时间戳或声明时长。
- 不足 1 秒的最终用量向上取整，重放帧和重复 sequence 不能重复计量。
- Provider `usage.duration` 单独记录用于成本核对，不能直接覆盖用户用量账本。
- 月度额度、Provider 成本和墙钟会议时长是三个不同指标，字段和日志不能混用。

### 11.3 数据模型

在 core 的下一序号 migration 中建立或扩展：

- `user_meeting_quota_overrides`
  - `user_id` 唯一。
  - 可选覆盖月度秒数、单场秒数和并发数。
  - 不存在记录时使用服务端默认策略。
- `meeting_usage_periods`
  - `user_id`、`period_start`、`period_end`。
  - `consumed_seconds`、`reserved_seconds`。
  - 唯一约束 `(user_id, period_start)`。
- `meeting_usage_reservations`
  - `reservation_id`、`user_id`、`meeting_id`、周期。
  - `granted_seconds`、`reported_seconds`、状态和过期时间。
  - `meeting_id` 唯一，重复创建不能重复预占。
- `meeting_usage_records`
  - 每场会议最终结算用量、Provider 用量、结算原因和时间。
  - `meeting_id` 与 usage kind 唯一，重复 finalize 不能重复扣减。

quota override、reservation status 和 settlement reason 都是闭集，必须在 biz 使用领域类型并在数据库增加 check constraint。

### 11.4 原子预占算法

`CreateMeeting` 在同一个短事务中：

1. 先按幂等键查询是否已有会议；重复请求直接返回原会议和已有 reservation。
2. 创建或锁定当前用户的 `meeting_usage_periods`，使用 PostgreSQL `SELECT ... FOR UPDATE` 或等价行锁。
3. 统计未结束且未过期的 reservation 和活跃会议数。
4. 校验 `active_count < max_concurrent_meetings`。
5. 计算 `remaining = monthly_limit - consumed - reserved`。
6. 计算 `granted = min(max_meeting_seconds, remaining)`。
7. `granted <= 0` 时返回 `MEETING_QUOTA_EXCEEDED`。
8. 原子创建 meeting、reservation，并增加 `reserved_seconds`。
9. 提交事务后才调用 vision；禁止在数据库事务中进行 gRPC 或 Provider 网络调用。

vision 准备失败时，core 通过幂等补偿释放 reservation 并把 meeting 标记为安全失败/取消状态，不能留下永久占用。

### 11.5 实时执行和上报

- core 将 `granted_seconds` 传给 vision 的 `PrepareTranscription`。
- vision 把该值放入服务端 session 和一次性 ticket claims，但不接受客户端覆盖。
- vision 根据唯一有效 PCM sequence 的累计字节执行本地硬限制。
- vision 每 30 秒以及 finish/fail/cancel 时向 core 上报单调递增的 `total_accepted_audio_seconds`。
- core 按 `(session_id, reported_total)` 幂等处理，只接受不回退的累计值。
- 达到 `granted_seconds` 后，vision 停止接收新音频、flush Provider 尾部结果并发送 `MEETING_QUOTA_EXCEEDED`；已经生成的最终片段仍须可靠同步。
- WSS 断开、vision 重启或 reservation 过期时，由 reconciliation 任务按最后上报值结算并释放未使用预占。

### 11.6 结算算法

正常 stop、额度耗尽、取消、失败和过期都调用同一个幂等 finalize：

1. 锁定 reservation 和 usage period。
2. `actual_seconds = min(reported_seconds, granted_seconds)`。
3. `reserved_seconds -= granted_seconds`。
4. `consumed_seconds += actual_seconds`。
5. 写入唯一 usage record 并把 reservation 转为终态。
6. 已终态 reservation 再次 finalize 返回原结果，不重复扣减。

如果 Provider usage 晚到，只更新成本审计字段，不再次扣用户月度额度。需要财务级修正时通过新的 adjustment ledger 记录，不直接覆写历史 consumed。

### 11.7 Redis 限流

- core 使用 Redis token bucket 或固定窗口限制用户创建会议频率。
- key 示例：`core:meeting_create_rate:v1:<user_id>:<window>`。
- TTL 必须覆盖窗口并自动清理。
- 限流返回 `MEETING_RATE_LIMITED` 和安全的 retry metadata。
- Redis 只承担短期限流；月度额度、reservation 和最终用量必须在 PostgreSQL。
- Redis 不可用时，新会议按安全策略拒绝或降级到 PostgreSQL 并发检查，策略必须配置并测试，不能静默无限放行。

### 11.8 查询接口

`GetMeetingQuota` 至少返回：

- `period_start` / `period_end`。
- `limit_seconds`。
- `consumed_seconds`。
- `reserved_seconds`。
- `remaining_seconds`。
- `max_meeting_seconds`。
- `max_concurrent_meetings`。
- `active_meetings`。

返回值全部由服务端计算；不得返回数据库内部 override 结构或其他用户信息。

## 15. B-700：vision 业务 WebSocket

目标：实现 uTools 可连接的公开 WSS，并将业务协议映射到 vision biz，不透传百炼协议。

### 15.1 Ticket

- vision 在 `PrepareTranscription` 中生成至少 256 bit 随机 ticket。
- ticket claims 包含 core 授予的 `granted_audio_seconds`，vision 只能收紧不能扩大。
- Redis 只保存 `sha256(ticket)` 对应的有界 session claims。
- TTL 默认 60 秒，可配置且有上限。
- 使用 Redis `GETDEL` 或等价原子操作实现一次性消费。
- 同一 ticket 并发消费只能成功一次。
- ticket 放在第一条 TLS 保护的 `start` 消息，不放 query。

### 15.2 WebSocket route

- 在 vision `internal/server` 注册自定义 route。
- server 负责 upgrade、Origin、消息类型、大小和 read/write deadline。
- service 负责业务消息到 biz 类型的显式转换。
- server 不直接访问 data/Redis/Provider。
- WebSocket 写入由单 goroutine 拥有。
- 所有队列有边界，慢客户端触发背压或安全关闭。

### 15.3 协议

必须实现：

- `start -> session_ready`
- binary `audio_chunk -> ack`
- `ping -> pong`
- `transcript_segment`，包含 `revision` 和 `isFinal`
- `finish -> session_finished`
- 结构化 `error`
- 配额耗尽时 flush 已接收音频并返回 `MEETING_QUOTA_EXCEEDED`，同时保留最后 ACK 和最终片段。

关键语义：

- WSS `open` 不等于 ASR ready；收到百炼 `task-started` 后才能返回 `session_ready`。
- ACK 只表示 vision 已接受帧，不表示永久保存或最终识别。
- 收到客户端 `finish` 后继续读取 Provider 尾部结果。
- 返回 `session_finished` 后再正常关闭。
- 客户端异常断开时取消或在短宽限期内等待 resume，不泄漏 Provider session。

### 15.4 测试

- 非 JSON 首消息、错误 version、错误音频格式和超大帧。
- sequence 重复、跳跃、倒退和超过重放窗口。

## 16. B-800：跨服务同步与停止闭环

目标：保证最终片段不只存在于当前 WebSocket，而是可靠进入 core 会议记录。

### 16.1 core -> vision

- data 层实现 `VisionTranscriptionGateway` gRPC adapter。
- 所有调用传递 context、deadline、request/meeting correlation metadata。
- `PrepareTranscription` 使用 meeting ID 和幂等键，重复调用返回同一有效 session 或明确新 ticket 语义。
- `PrepareTranscription` 必须携带 core 生成的 reservation ID 和 `granted_audio_seconds`。
- core 不读取 vision 数据库或 Redis ticket key。

### 16.2 vision -> core

- data 层实现 `FinalTranscriptSink` gRPC adapter。
- 最终片段批量提交，避免每个字或每个 partial 一次 RPC。
- 每批带 meeting ID、session ID、稳定 segment ID 和 sequence。
- core 使用数据库唯一约束和 biz 幂等校验去重。
- core 暂时不可用时，vision 使用 outbox/待同步记录有界重试，不能丢弃最终片段。
- 不在数据库事务中调用网络。
- vision 定期调用 `ReportTranscriptionUsage`，使用累计 accepted seconds；core 拒绝回退值并幂等更新 reservation。

### 16.3 Stop 闭环

1. uTools 发送 WebSocket `finish`。
2. vision 发送百炼 `finish-task` 并接收最后最终片段。
3. vision 确认最终片段已经进入可靠同步路径。
4. vision 返回 `session_finished`。
5. uTools 调用 core `StopMeeting`，或客户端/服务端按冻结协议决定先后顺序。
6. core 幂等更新 meeting/transcription stage。
7. core 幂等 finalize reservation，把实际用量计入本月并释放未使用预占。

必须在 B-100 中明确步骤 1 与步骤 5 的顺序以及重复请求行为，不能由客户端和服务端各自猜测。

### 16.4 本轮会议终态

本轮不实现 LLM 纪要，因此停止后：

- transcription stage 可以达到 `SUCCEEDED`。
- meeting 可以保持 `PROCESSING`，等待后续 summary stage；或者使用已经在 B-100 明确定义的阶段化状态表达。
- 不允许返回虚假的 `COMPLETED` 和空 summary。

- 用量 progress、finish、fail、cancel 和 expire 重试不重复扣减额度。
